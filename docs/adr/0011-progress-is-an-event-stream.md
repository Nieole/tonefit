# ADR 0011：进度是事件流，开工前先预扫

状态：已采纳（2026-08-26）；决定第 3 条修订（2026-09-03，预扫改成只数不留）

## 背景

`Progress` 只有三个方法：一卷开始、走完一步、一卷结束。它足够画一条横条，说不出别的——
在哪一遍、刚才哪一页失败了、这一卷是被跳过的、全局还剩几卷。

同时 `Report` 已经是完整的结构化数据，只是**跑完才交出来**。长任务里这两件事撞在一起：
屏上是一条什么都不说的横条，而所有说得出口的东西都攒在一个跑完才出现的对象里。

全局进度还差一个数。一个卷要走多少步，得先枚举它的成员才知道，而枚举发生在处理那一卷时。
「总共还要多久」因此在开工时无从算起。

## 决定

1. **报到的东西从「步」加宽成「事件」**：`Progress` 换成一个非穷尽的事件枚举加单个回调。
   回调是**双向**的——它收下事件，回一个指令：继续、收尾、中止。取消因此不必另开一条信号通路，
   而「第二遍之前停下来问一句」（ADR 0012：续做）与「按停」走的是同一条回路。
2. **一卷跑完的那个事件直接带上它的 `VolumeReport`**——事件流就是报告的增量。
   调用方边跑边把报告攒出来：CLI 攒完在最后一次性渲染，TUI 攒到哪儿画到哪儿。
   两者拿的是同一份数据，不是两套。
3. **开工之前先预扫**：把点名的卷全枚举一遍，算出全局总步数。只列成员、不碰像素；
   **数完就把卷放掉**，只留下这一卷的路径与几个数，处理那一卷时按路径再开一次。
   归档卷的中央目录因此读两遍——换来的是句柄与常驻内存**不随点名的卷数长**，
   成百上千个卷点得动。

## 后果

**好的：**

- TUI 与 CLI 共用一份数据。「跑到一半看到的」与「跑完看到的」不会长得不一样。
- 以后要多报一件事只加一个枚举变体，实现方不必跟着改——现在有三个实现方：CLI、TUI、用例里的计数器。
- 全局 ETA 成立，而它正是长任务里唯一有人真正想知道的数。
- 预扫顺带把「一卷点不开」提前到一页都没做之前（见 `CONTEXT.md` 的《失败》：卷级失败）。

**要认的代价：**

- `run` 的结构要改：枚举从 `process_volume` 里提到前面，而处理那一卷时还要按路径再开一次。
- 归档卷的中央目录读两遍、目录卷走两遍目录。这一笔随一个卷长，不随点名的卷数长。
- 两遍之间源变了的话，做的与报的是**重开的那一份**；开工那条事件报出去的全局总步数
  仍是预扫那一遍算的，而那个数本来就是上界。
- 预扫在慢盘与网络盘上要花时间，那段时间屏上什么都没发生。
- 全局总步数仍是**上界**——幂等命中的卷提前收摊，预扫算进去的那几段不会走。
- `VolumeReport` 进了事件就等于进了对外 API，它的字段从此不能随手改。
- 回调有了返回值，就有了「可能很久不返回」这个性质：会话在决策点上等人。
  实现方不能在持锁的地方调它，用例里的计数器不受影响。

## 备选方案

- **保留三个方法，往上加几个**——每多报一件事就改一次 trait 形状，三个实现方跟着改三处。
- **不预扫，全局按卷数给**——12 卷大小差 10 倍时，那个百分比与剩余时间毫无关系。
- **不预扫，全局按字节加权**——字节与处理时间只是相关：高压 JPEG 与无损 PNG 差得很远；
  而且最终仍要枚举，只是晚一点。
- **事件只带页数与状态码，报告仍等到最后**——那就要维护两套渲染，而两套渲染必然漂移。
- **观察者保持单向，取消另走一个共享信号**——最好实现、最好理解，但表达不了「停下来等人拿主意」，
  于是续做要么没有家，要么得在库里另开一个 `Session` 类型装它。

## 不要做的「简化」

「预扫既然把成员都列出来了，顺手把大小与修改时间也存下来，下次就不用扫了。」
那是一份全库索引，ADR 0009 关掉的正是它。预扫的作用域是**这一趟点名的卷**，
活在一次运行之内，不落盘。
