# ADR 0021：PNG 是唯一的输出编码器

状态：已采纳（2026-10-27）；**取代 ADR 0004**

## 背景

ADR 0004 在 2026-08-25 收下了四条决定：默认 PNG、`--codec=avif` 作显式可选、编码器抽成接口、
判据层对编码器无知。它同时押了两笔没结的账：**AVIF 的页内记录该挂在哪儿，尚未调研**；
以及整篇决定都建在一个**没量过**的假设上——AVIF 编回来还保不保得住这个工具的输出格点。

两笔账到 2026-10 都结了，而结论都指向反面：

1. **页内元数据载体：这条链上过不去。** `image` 的 `AvifEncoder` 只有一个装任意字节的口子
   （Exif 项），而运行时那一侧 `AvifDecoder` 与 `mp4parse` 都没有 Exif 访问器——
   读回来恒 `Ok(None)`，与「这张图本来就没有记录」返回值逐字相同，**不报错**。
   逐条依据见 `docs/research/avif-in-page-metadata-carrier.md`。
   「载体」这个词要求的是「字节挂得住」还是「链上现成读得回」，ADR 0009 那句没写开，
   2026-09-20 拍板按后者读（`encoder-gate/02` 的 Q958）：**AVIF 过不了这道闸**。
2. **《落格》：这条链上编不出无损 AVIF，于是过不去。** `ravif` 把 `quality = 100` 换成
   quantizer 0，而 `rav1e` 0.8.1 不做无损——`src/rate.rs` 的 `min_qi` 一路 `.max(1)`，
   `src/segmentation.rs` 明写「never bringing qidx below 1」。21 组实测里 17 组解回来的像素
   与写出去的不相等；而近似无损在 1~4bit 内容上比 PNG 大 **9~702 倍**
   （见 measurements 的《AVIF 无损输出：这条依赖链上做不到，而近似无损在 1~4bit 内容上大 9~702 倍》）。
3. **可读性这一头也更紧了。** 四台目标设备的自带阅读器本来就不认 AVIF
   （measurements 的《设备支持的图片格式》），而 2026-08 时还能指望的第三方阅读器同样不行：
   KOReader 到今天仍读不了 AVIF（koreader#10973 开着，koreader-base 的 `feat: add AVIF support`
   PR #2383 未合并）。

ADR 0009 已经写下了两道前置：**一个编码器进不了这个项目，除非它有页内元数据载体**
（《不要做的「简化」》末段），以及《落格》（`GLOSSARY.md` 的《量化》）。
这两道今天都不是「再努一把」的问题——它们各自卡在上游，不在我们手上。

## 决定

1. **PNG 是唯一的输出编码器。** 不做 `--codec`，不做第二套编码路径，不抽编码器接口
   （ADR 0004 决定第 3 条随之退场：只有一个实现时不抽，抽了也只是给一个不存在的岔路付利息）。
2. **第二个编码器要同时过两道闸，两条都是机械可验的：**
   - **《落格》**（**《落格》，见 `GLOSSARY.md` 的《量化》**）：它已经有机械形式——
     `tests/pipeline.rs::every_candidate_the_pipeline_writes_comes_out_on_grid`。
   - **页内元数据载体**：这条依赖链上有**现成的读回口子**把《记录》取回来（ADR 0009）。
     口径是「链上现成 API 读得回」，不是「字节挂得住、我们自己走箱取得回」（Q958）。
3. **WebP、JPEG、AVIF 三个具体提案各自否掉的理由不同，写在同一处免得再问一遍：**
   - **AVIF**：上面《背景》那三条（两道闸都过不去，且可读性那一笔落在用户身上）；
   - **WebP**：既没有位深字段（本项目的机制无处附着），也不在任何一台目标设备的格式表里；
   - **JPEG**：设备都认，但**有损**——它把 29 级灰调还成 215~217 级（measurements 的
     《有损转存与灰调级数》），《落格》当场不成立。理由是「有损」，不是「设备不支持」——
     后者查漏补得上，前者补不上。
4. **不实现「两个编码器都试编码、每页挑体积小的那个」。** 三条理由原样留在 ADR 0004 的
   《不要做的「简化」》里，本篇引用不复述：可读性不再确定、两条曲线形状不同单一阈值比不了、
   按体积选优会让 2bit 以下那段非对称看不见。
5. **什么时候翻案。** 任一条成立时才重新问第二个编码器：一是链上出现**真无损**的 AVIF 编码器
   且**链上读得回**页内记录；二是目标设备与用户手上的阅读器普遍认它，且第一个条件的代价
   被实测证明小于它买到的。今天两条都不成立，而「先写上，将来再说」不算第一条。
6. **那条分工照旧**：灰阶档位与抖动模式在编码**之外**（判定层的事），调色板模式在编码**之内**
   （同一个候选按体积挑颜色类型，写出的像素一个不动）。它不依赖有几个实现。

## 后果

**好的：**

- 输出只有一种格式、一条质量-体积曲线，画质门槛只需在它上面标定一次。
- 《记录》只有一个载体（PNG tEXt），幂等只有一条读回路径，不必维护第二份 ISOBMFF 走箱。
- 依赖树里没有 AV1 编码器（`ravif`／`rav1e`／`avif-serialize` 都不进产物）：
  编得更快、二进制更小，`image` 的 AVIF 特性只剩解码那一半（`avif-native`）。
- 默认输出在四台目标设备的自带阅读器上开箱可读，这一条不必靠用户自己核。

**要认的代价：**

- **用户拿不到 AVIF／WebP 产物**，即便他手上那个阅读器读得动。这是真的损失：
  中高质量区 AVIF 在体积与误差两轴上都优于 PNG（ADR 0004《后果》里那句照旧成立），
  只是那个质量区**本项目的输出不在里面**——1~4bit 位深是它的主场，而那一格 AVIF 到不了。
- 将来真要接，两样前置**都不在我们手上**：要等上游补 Exif 访问器，也要等一个真做无损的
  AV1 编码器。这一条不由我们的排期决定。
- 这条决定把「输出格式」钉在一条依赖链的一个实现上。换掉 PNG 的代价因此包含「重做记录载体」
  与「重标定阈值」两笔，不只是换一个函数。

## 备选方案

- **全面改用 AVIF**：三家自带阅读器与 KOReader 都读不了，输出在目标设备上打不开。
- **`--codec=avif` 显式可选**（ADR 0004 决定第 2 条）：本篇取代它，理由见《决定》第 2 条。
- **只给彩页做有损 AVIF**：彩页不量化，《落格》管不着它，而连续调正是 AVIF 的强项。
  仍然否掉：它要另立一个**质量档位**（未标定，且没有一块彩色面板可标定，见 `GLOSSARY.md` 的
  《尚未确立》），只在彩色面板上有活，可读性那一笔代价照旧——买到的是一小撮页的体积，
  付出的是第二套编码路径、第二个质量刻度与第二个记录载体。
- **换一个编码器求真无损 AVIF**（`libavif`／libaom，C 依赖）：三条闸门各要备一份新的系统依赖
  （`docs/agents/gate.md` 那张表要多两行），而 1~2bit 内容上 AVIF 无损没有理由小于 PNG 的
  位打包——那一格要实测，但两个轴上都看不到收益。
- **WebP lossless**：设备不支持，且没有位深字段，本项目的机制无处附着。
- **JPEG**：有损，见《决定》第 3 条。

## 不要做的「简化」

**「AVIF 那一趟把《落格》松开，反正阅读器会自己降一遍。」**
那正是这个工具要防的事。阅读器拿到连续调之后自己再量化，用的是**它的**规矩、它的网格、
它对抖动的处理——而抖动本来就只有「1:1 贴到面板」这一条路成立（ADR 0007）。
放开这一条，掉的不只是「落格」这三个字：抖动的字节照付，画质收益**不可知也不可验**。

**「先写 AVIF、记录以后再说。」**
没有记录就没有幂等：一个 avif 页读回来恒是「没有记录」，与「这是别人写的页」分不开，
每一趟都要整卷重做。ADR 0009 的《不要做的「简化」》把「把记录挪出文件」否掉的那一段，
换成「干脆不写记录」也一样成立——差别只是从把依据搬走，变成把依据扔掉。

**「加一个 `--codec=avif` 但不进参数哈希。」**
漏一项的下场是改了它的那一趟被幂等静默跳过：用 AVIF 重跑一遍，得到的还是 PNG。
这一类事故 ADR 0002 的《后果》里记过一次，这是同一个形状。
