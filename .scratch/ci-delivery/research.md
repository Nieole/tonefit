# CI / first prerelease — research, not an implementation plan

Researched **2026-10-31 UTC** for public `Nieole/tonefit`. No source, spec, workflow, binary, or secret changes. Product choices below remain proposals. Scope authority: [CI 与阶段交付 spec](spec.md): PR/main CI, four native targets, unzip-and-run including required runtimes/licenses/checksums, repair Q995/platform blockers rather than skip tests, and actually publish the first prerelease only after all checks pass.

## 1. Four native builds are available (including Intel Mac)

Use explicit OS/architecture pairs, not `*-latest`. Current official [runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [runner-images table](https://github.com/actions/runner-images/blob/main/README.md) list:

| Native runner candidate | Rust host/target | Build prerequisites |
|---|---|---|
| `windows-2022` (x64; also `windows-2025` available) | `x86_64-pc-windows-msvc` | MSVC x64 developer environment/Windows SDK; pkg-config; Meson/Ninja/NASM or pinned vcpkg |
| `ubuntu-22.04` (x64) | `x86_64-unknown-linux-gnu` | C/C++ compiler; pkg-config; Meson/Ninja/NASM |
| `macos-15` (ARM64) | `aarch64-apple-darwin` | Xcode command-line toolchain; pkg-config; Meson/Ninja; native assembler |
| `macos-15-intel` (x64) | `x86_64-apple-darwin` | Same, with NASM for x86 assembly |

These Mac labels are **standard**, not the paid `-large`/`-xlarge` labels; standard runners are free for public repositories. `macos-26`/`macos-26-intel` also exist ([GitHub announcement](https://github.blog/changelog/2026-02-26-macos-26-is-now-generally-available-for-github-hosted-runners/)). The current image table marks macOS 14 deprecated. Intel availability is real today, not a perpetual availability promise. Explicit labels still receive image/tool updates: record the image version from each job log. [Source: runner reference/table above.]

**Rust 1.98 is released and has all four host toolchains.** Directly read the [1.98.0 distribution manifest](https://static.rust-lang.org/dist/channel-rust-1.98.0.toml): date `2026-08-20`, and `available=true` for `rust`, `rustc`, `cargo`, `rust-std`, `clippy-preview`, `rustfmt-preview` on all four triples. Pin `1.98.0` explicitly and install those components; do not assume the runner's preinstalled stable matches `Cargo.toml`'s `rust-version = "1.98"`. In [1.98 platform support](https://github.com/rust-lang/rust/blob/1.98.0/src/doc/rustc/src/platform-support.md), Apple ARM64/Linux x64/Windows MSVC x64 are Tier 1 with host tools; Intel macOS is Tier 2 with host tools, not unavailable. Native runners avoid the host-`cfg!` pitfalls visible in `unrar-ng-sys`'s build script. Verify actual host architecture before building. Sources for tool availability: [Windows image](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md), [Linux image](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2204-Readme.md), [Mac Intel](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-Readme.md), [Mac ARM](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-arm64-Readme.md).

## 2. Keep dav1d and AVIF; static native linkage is supported

Repository evidence: [`Cargo.toml`](../../Cargo.toml), [`Cargo.lock`](../../Cargo.lock) lock `image 0.25.10` with runtime `avif-native`, `dav1d 0.11.1`, `dav1d-sys 0.8.3`, `system-deps 7.0.8`, and `unrar-ng(-sys) 0.7.7`. The high-level UnRAR wrapper is patched in [`vendor/unrar-ng/PATCH.md`](../../vendor/unrar-ng/PATCH.md); do not replace it with the registry wrapper while packaging. Dev-only `image/avif` is an encoder for fixtures, not a replacement runtime decoder.

Inspected exact downloaded registry source at `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/` (matching lockfile versions); public equivalents:

- [`dav1d-sys 0.8.3 Cargo.toml`](https://docs.rs/crate/dav1d-sys/0.8.3/source/Cargo.toml) requires native **dav1d >=1.3.0** via system-deps, not native dav1d version 0.8.3.
- Its [`build.rs`](https://docs.rs/crate/dav1d-sys/0.8.3/source/build.rs) registers an internal builder: clones VideoLAN tag **1.5.0**, runs Meson `-Ddefault_library=static`, Ninja, install, and probes generated pkg-config metadata. No decoder swap or Cargo feature removal is needed.
- [`system-deps 7.0.8`](https://docs.rs/system-deps/7.0.8/system_deps/) supports **`SYSTEM_DEPS_DAV1D_LINK=static`** for an externally built static library discovered by pkg-config, and **`SYSTEM_DEPS_DAV1D_BUILD_INTERNAL=always`** to force the internal builder. `auto` only builds when discovery fails; default `never` does not vendor anything. `PKG_CONFIG_PATH` selects the staged `.pc` directory. Installing a static library without requesting static linkage is not sufficient evidence of the final link.

Two viable approaches to test, not a decided policy:

1. **Explicit, pinned native dependency build**, then pkg-config + `SYSTEM_DEPS_DAV1D_LINK=static`: best control over source hash, Meson release/CRT/deployment flags, and licenses. dav1d [Meson options](https://github.com/videolan/dav1d/blob/1.5.0/meson_options.txt) retain both 8/16-bit decoding by default and enable assembly; [Meson built-ins](https://mesonbuild.com/Builtin-options.html) supply `--buildtype=release`, `--default-library=static`, `b_vscrt`. Build tools are CI prerequisites only. No `-march=native`/`target-cpu=native` for redistributable executables.
2. **Crate's internal builder**: less orchestration, but hardcoded 1.5.0 tag clone is outside Cargo.lock's source checksum, lacks explicit release/CRT selection, and its helper does not inspect subprocess exit success before subsequent operations. It is not a cryptographically pinned vendored tarball or an established Windows packaging solution. Verify before adopting; never describe Cargo.lock alone as pinning that native checkout. [Exact build.rs above.]

**Windows:** official [vcpkg dav1d port](https://github.com/microsoft/vcpkg/blob/master/ports/dav1d/portfile.cmake) acquires NASM for x64, builds with Meson, honors library linkage, fixes pkg-config, and installs upstream copyright files. Its [current manifest](https://github.com/microsoft/vcpkg/blob/master/ports/dav1d/vcpkg.json) is native 1.5.4, license `BSD-2-Clause AND ISC`; pin the vcpkg commit/baseline rather than floating master. This crate uses **pkg-config/system-deps**, not automatic vcpkg discovery: point pkg-config at the chosen **release** triplet library metadata. Do not mix debug/release libraries.

Library linkage and CRT linkage are separate. [`x64-windows-static`](https://github.com/microsoft/vcpkg/blob/master/triplets/x64-windows-static.cmake) selects static library + static CRT; `x64-windows-static-md` is a community triplet with static library + dynamic CRT ([triplet variables](https://learn.microsoft.com/en-us/vcpkg/users/triplets), [Windows triplets](https://learn.microsoft.com/en-us/vcpkg/users/platforms/windows)). For a static-CRT candidate, align Rust `-C target-feature=+crt-static`, dav1d `/MT` (Meson `b_vscrt=mt` or matching vcpkg triplet), and cc-rs/UnRAR compilation; inspect the actual commands and PE imports. Rust's flag does not magically change a separately built dav1d library. [Rust linkage](https://doc.rust-lang.org/reference/linkage.html), [cc-rs API](https://docs.rs/cc/latest/cc/struct.Build.html), [Meson options](https://mesonbuild.com/Builtin-options.html).

**UnRAR is already a static archive, not a standalone DLL requirement.** Exact [`unrar-ng-sys build.rs`](https://docs.rs/crate/unrar-ng-sys/0.7.7/source/build.rs) compiles vendored C++14 into `libunrar.a`; however static archive ≠ statically linked C++ runtime. It explicitly calls `cpp_link_stdlib(None)` and probes `-stdlib=libc++`; investigate Linux unresolved C++ symbols/runtime linkage on the native job. Windows needs native MSVC C++ tooling, not MinGW as an accidental substitute. Audit transitive native libraries too, not just dav1d.

## 3. Minimum OS: options to present, NOT promises or product decisions

Rust's support floor is only a lower bound, not tonefit's proven floor. [Versioned Rust platform table](https://github.com/rust-lang/rust/blob/1.98.0/src/doc/rustc/src/platform-support.md) and [Apple page](https://github.com/rust-lang/rust/blob/1.98.0/src/doc/rustc/src/platform-support/apple-darwin.md) give Linux kernel 3.2/glibc 2.17, Windows 10+/Server 2016+, Mac Intel 10.12+, Mac ARM64 11+. Dependencies/SDKs/linker symbols can raise these.

| Candidate outcome | Tradeoff / evidence needed |
|---|---|
| Linux glibc **2.35+**, Ubuntu 22.04-class baseline | Straightforward native `ubuntu-22.04` build; Jammy ships [glibc 2.35](https://packages.ubuntu.com/jammy-updates/libc6). Inspect actual ELF symbol requirements and test on minimum runtime; building there does not prove every glibc 2.35 distribution works. Ubuntu 24.04 ships [2.39](https://packages.ubuntu.com/noble/libc6), so building on it does not establish an older floor. |
| Linux glibc **2.28+**, or ambitious **2.17+** | Build *all* native objects and Rust binary against a correspondingly old userspace/sysroot in an x64 Linux container, then test on it. More build-tool provisioning and ongoing maintenance. Rust's 2.17 floor alone is insufficient. A musl alternative is another target/behavior validation effort, not a free flag change to this four-target scope. |
| Windows **10 x64+** (or narrower Windows 11 policy) | 10 matches Rust's baseline; Server runner tests are not Windows 10 client validation. Static CRT avoids a redistributable installer; dynamic CRT requires permitted app-local runtime files to satisfy unzip-and-run. Neither strategy eliminates system DLL dependencies. |
| macOS **11+ both architectures** vs **13+/14+** or runner-aligned **15+** | 11 is a plausible unified build target, not validated support. Newer floor reduces old-OS testing burden. Export `MACOSX_DEPLOYMENT_TARGET` consistently for Rust/C/C++; inspect binary AND bundled dylib minimum versions and test the oldest claimed system. Hosted macOS 15 testing cannot establish 11 support. Intel 10.12 is Rust's theoretical floor, not a sensible unsupported promise. |

Linux: inspect `readelf -d`, `readelf --version-info`/`objdump -T` for `GLIBC_*`, `GLIBCXX_*`, `CXXABI_*` and all `NEEDED` entries. Static dav1d does **not** make glibc static or remove C++ runtime requirements. Options for a required non-system C++ runtime are static linkage with applicable exception/license review or bundled libraries with relative `$ORIGIN` search paths; do not casually bundle glibc/loader as ordinary sidecar libraries. [GNU C++ ABI/versioning](https://gcc.gnu.org/onlinedocs/libstdc++/manual/abi.html), [ELF loader search rules](https://man7.org/linux/man-pages/man8/ld.so.8.html), [GCC runtime exception](https://www.gnu.org/licenses/gcc-exception-3.1.html). Final policy must specify which base OS libraries count as system-provided.

macOS: prefer static dav1d to avoid Homebrew absolute paths. If using shared dav1d, include its entire non-system dylib dependency closure, rewrite install names/rpaths relative to the executable (`@executable_path`/`@loader_path`/`@rpath`), and audit with `otool -L` plus load commands. Changes by `install_name_tool` invalidate signatures: complete relocation/stripping first, sign libraries then executable, verify final signatures, then archive/hash. Ad-hoc signing is not Developer ID identity/notarization; it does not promise no Gatekeeper warning after a browser download. An unsigned/ad-hoc first release versus Developer ID/notarization remains a user choice, with a real quarantine/download test required. [Apple dynamic-library guide](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/RunpathDependentLibraries.html), [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html), [Developer ID](https://developer.apple.com/developer-id/).

## 4. Archive contents and license burden

Candidate contents: executable, any proven necessary sidecar runtimes, usage/minimum-OS/security-warning notes, root MIT `LICENSE`, `THIRD-PARTY-NOTICES.md`, complete applicable third-party license texts, build provenance (commit/tag, Rust/native dependency versions and target). Publish **SHA-256 of final archives**, after any signing/relocation, in `SHA256SUMS`; hashes detect corruption but do not alone authenticate the publisher. Windows ZIP; Unix tar.gz preserves executable bits. These are packaging recommendations, not new contracts.

- **dav1d BSD-2-Clause** requires copyright/conditions/disclaimer in binary distribution materials even when statically linked ([COPYING](https://github.com/videolan/dav1d/blob/1.5.0/COPYING)). x86 assembly has an additional **ISC** notice ([x86inc.asm header](https://github.com/videolan/dav1d/blob/1.5.0/src/ext/x86/x86inc.asm)); include actual selected native version's notices, not only `dav1d-sys`'s MIT wrapper license. Current vcpkg port explicitly installs both files.
- **Fonts:** [`THIRD-PARTY-NOTICES.md`](../../THIRD-PARTY-NOTICES.md), [`src/calibrate/glyphs.hex`](../../src/calibrate/glyphs.hex), [`licenses/OFL-1.1.txt`](../../licenses/OFL-1.1.txt) identify embedded GNU Unifont 16.0.01 subset under **OFL 1.1**, not a requirement to license the whole CLI under GPL. Preserve OFL/copyright and assess reserved-name/modification rules if changing the subset. [Official OFL text](https://openfontlicense.org/open-font-license-official-text/).
- **UnRAR:** include existing [`licenses/UnRAR.txt`](../../licenses/UnRAR.txt) and notices specifying 7.21.1, along with vendored Rust wrapper MIT/Apache license material. UnRAR is not MIT: its compression-algorithm/compatible-archiver restrictions remain. [Repository notices](../../THIRD-PARTY-NOTICES.md), [RARLAB source distribution](https://www.rarlab.com/rar_add.htm), exact dependency `vendor/unrar/license.txt`/`version.hpp`.
- **Other dependencies/runtimes:** inventory the actual release feature/target dependency graph, not merely every dev dependency in Cargo.lock. MIT/Apache and other required notices remain relevant for static code. GNU runtime redistribution needs its applicable GPL + runtime-exception assessment; Microsoft runtime redistribution must be from permitted REDIST files under the relevant Visual Studio license, **not arbitrary DLLs copied from System32**, and never debug CRT. App-local deployment can avoid an installer. [Microsoft redistribution/license guidance](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170), [app-local deployment](https://learn.microsoft.com/en-us/cpp/windows/walkthrough-deploying-a-visual-cpp-application-to-an-application-local-folder?view=msvc-170).

## 5. Checks and secure, all-green publication boundary

**Repository gates:** [`docs/agents/gate.md`](../../docs/agents/gate.md) defines `cargo xtask gate` (default tests; no-default-feature tests in separate target dir; profiling check) and `cargo xtask polish` (fmt, both clippy variants, docs). Run those existing conventions on all four platforms; use locked dependency resolution where supported by orchestration. Do not substitute `cargo build` for acceptance. Any design-export checks that are applicable must also join the release barrier. Existing sample-based harnesses explicitly report absent `TONEFIT_SAMPLES`; enumerate these outcomes honestly rather than claim external-material tests ran ([tests/smoke.rs](../../tests/smoke.rs), [tests/perceptual.rs](../../tests/perceptual.rs)). No new skipping/ignoring to make CI green.

**Concrete blockers found by reading, not newly executed failures:** Q995 is in [`tests/concurrency.rs:692–778`](../../tests/concurrency.rs): `/proc/self/fd` detection otherwise falls back to a Windows rename-denial assumption, which does not detect held files on Mac. Existing research already proposes Mac descriptor enumeration + `fcntl(F_GETPATH)` while retaining a positive control ([Q995 owning note](../green-counts/issues/10-the-concurrency-check-sees-on-macos.md)). [`tests/stop.rs`](../../tests/stop.rs) already has a crate-wide `#![cfg(unix)]`: Windows therefore currently runs **zero** stop-process tests; it is a coverage gap, not an unguarded compile failure. Removing that guard alone would expose Unix-only `mkfifo`, `OpenOptionsExt`, `kill`/`SIGINT` and fail Windows compilation. Windows needs equivalent real console Ctrl-C behavior coverage and deterministic synchronization, not removal of that test target. A read-only follow-up checked `ctrlc 3.5.2`'s own Windows test helper: it owns a separate console and broadcasts `CTRL_C_EVENT`; do not assume targeting a child PID/new process group or substituting Ctrl-Break proves Ctrl-C delivery. Further native runtime/link blockers may emerge only on CI.

**Security recommendations grounded in [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) and [token permissions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication):**

1. Pin every action/reusable workflow to verified full commit SHAs; pin native downloads/source hashes and toolchain versions. Default `permissions: contents: read` (or none where possible); grant `contents: write` only to the final trusted publisher. Disable persisted checkout credentials where not needed.
2. PR validation uses `pull_request`, no secrets/write token, no release access; do not checkout/run PR code under privileged `pull_request_target` or privileged `workflow_run`. Separate caches/artifact trust domains; never promote a fork PR artifact into a release. Treat branch/tag/title text as untrusted data, not interpolated shell code. [GitHub compromised runners](https://docs.github.com/en/actions/concepts/security/compromised-runners).
3. Validate stage-tag syntax and any version mapping (exact naming remains open); resolve annotated/lightweight tag to **one full commit SHA**. Fetch real `origin/main` history and require that commit be an ancestor of main (`git merge-base --is-ancestor <sha> origin/main`); requiring main HEAD equality would be a separate, stricter policy. Protect main and stage-tag creation/movement via rulesets. Every build/check uses that SHA and verifies HEAD; the publisher rechecks the remote tag before publication. [Git ancestry command](https://git-scm.com/docs/git-merge-base), [tag events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push), [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).
4. Re-run the full acceptance/package matrix for the tagged commit, or strictly verify successful checks/artifacts for that exact SHA and trusted workflow. A green earlier main run at a different SHA is insufficient. Use one final publisher with `needs` on **every** required check/build/packaged-runtime job; require all success, four distinct expected targets and exact asset set, no `continue-on-error`. `fail-fast: false` helps diagnose every platform; it does not relax the barrier. Avoid an `always()` publisher that mistakes skipped/cancelled work for success. [Job dependency semantics](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs), [matrix semantics](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations).
5. Package once from successful release builds; archive names/provenance carry target + same SHA/tag. On a clean runtime without build-tool PATHs/Homebrew/vcpkg dav1d, extract those **actual archives**, execute help/version AND decode/transform AVIF, RAR, and representative other formats; check libraries/imports and exit behavior. A full dev runner smoke test can hide missing runtime libraries. Do not rebuild different bytes after these tests.
6. **One release-level visibility transition, not four matrix uploads to a live release:** after all gates and local checksum verification, create a **draft prerelease** tied to the already-existing validated tag, upload every archive/notices/checksum asset, verify exact names/count/sizes and round-trip downloaded hashes, then publish by clearing draft with prerelease set. On failure leave draft unpublished (or clean it up); reruns must distinguish owned drafts from published releases and avoid replacing live assets. Serialize release attempts for a tag. GitHub uploads are separate API calls, not a transactional multi-asset upload: draft-then-publish prevents an intentionally half-populated *published* release, not every possible network/CDN failure. Consider enabling immutable releases: GitHub explicitly recommends draft/upload/publish so assets lock only when complete. [Release REST API](https://docs.github.com/en/rest/releases/releases), [asset API](https://docs.github.com/en/rest/releases/assets), [managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [immutability](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases). CLI `--verify-tag` avoids silently creating a missing tag ([gh release create](https://cli.github.com/manual/gh_release_create)); it does not itself prove ancestry or all-checks-green.

## 6. Explicit uncertainties / only actual CI or release testing can prove

- No gates or binary builds were run for this research-only task. Q995/platform findings are source evidence, not a fresh test report. First fix and run **all** tests on all four native architectures; retain positive controls and behavior equivalence.
- Actual static dav1d/UnRAR/CRT link commands and resulting PE/ELF/Mach-O dependency closure, pkg-config interoperability on MSVC, C++ symbols on Linux, and runtime AVIF/RAR success need real builds. Do not assert “one dependency-free binary” yet.
- Claimed minimum OS requires final-binary inspection **and execution on that OS**; macOS 11 and Windows 10 client hosts are not supplied by the proposed hosted matrix. Older Linux containers test userspace, not an older host kernel. Hosted-runner tests alone prove only those images.
- Quarantine/Gatekeeper behavior after browser download, final ad-hoc signature validity, and any Developer ID/notarization or Windows signing experience need end-user-path testing; no signing identity, credentials, binaries, or signing-policy decision was involved here.
- Final license inventory depends on native version/CRT choice and actual shipped dependencies. Neither current root notices nor Cargo metadata alone is a complete distribution notice bundle.
- Stage-tag naming/version mapping, OS floor, signing expectations, sample-fixture availability and maintenance, and immutable-release setting remain decisions for the user/design phase. Actual first prerelease requires trusted workflows merged to main, a successful real CI run, and successful final publication; research notes cannot claim those occurred.

Evidence method: official documentation/source search; direct HTTP reads of runner table, Rust 1.98 manifest/versioned platform docs, dav1d/vcpkg sources; local exact-version Cargo registry and repository inspection. The content-fetch service failed for several URLs, so direct HTTP/source reads and official search results were used instead. No secondary blog was relied on for a technical conclusion.
