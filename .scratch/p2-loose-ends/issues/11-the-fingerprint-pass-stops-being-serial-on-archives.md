# 11 — 归档卷的幂等这一道不再串行

**What to build:** 跑一批归档卷的人，四分之一的墙钟花在幂等那一道上——剖面量到它是三段里
第二大的一块，仅次于第一遍，而它几乎全是 deflate：成员绝大多数是 PNG，压缩比接近 1，
白解一遍；喂哈希本身读作 0.0%。那一段没有可与之重叠的计算，整段暴露在墙钟上。

**这一票要改一条领域决定**：`CONTEXT.md`《I/O 与并发》明写「一个 ZipArchive 就是一个游标，
读取恒串行，点名也改不了」。改法是把**幂等那一道**排除在这条之外——同一个文件开几个
独立句柄，各解各的成员，哈希那一端仍按成员序喂。第一遍与第二遍照旧串行。

指纹逐字节不变是硬约束：并行的是**解**，不是**喂**。喂的次序变了，幂等就整个塌了
（上一趟的输出会被当成不匹配，全部重做）。

收停车场的 **Q78**。数与推法在 measurements 的《三段各占多少》与《分阶段耗时剖面》。

## 落地记录

### `IoPlan` 从一个数变成**两路**，`ChosenBy` 一格没加

票面点名要先拍板的那件事：一个卷现在有两种读法，而 `IoPlan` 只有一份。三条出路里选了
**加一格，而那一格与原来那一格同形**：

```rust
pub struct Readers { pub count: usize, pub chosen_by: ChosenBy }

pub struct IoPlan {
    pub medium: Medium,
    pub readers: Readers,      // 两遍那一路
    pub fingerprint: Readers,  // 幂等那一道
}
```

`decide` 先按 `--io-mode` 与介质定出一个数，**幂等那一道拿的就是它**——那一道给每条读取
线程一个自己的句柄，读法与目录卷同形，容器形态不参与。归档卷的两遍另算，恒为
`Readers { count: 1, chosen_by: ArchiveScan }`。

**没有分成两份 `IoPlan`**：报告一卷印一行，读的人要的是「这一卷是怎么读的」一个答案，
而不是去对两份计划里哪一份说的是哪一段。**也没有让幂等那一道绕开 `IoPlan`**：那样
`--io-mode serial` 就按不住它——用户点名串行、而那一道照旧派满核数，报告说的就不是实话了。

**`chosen_by` 跟着那一格走，而不是一个卷一个。**这是为了同一条「说实话」：归档卷点名串行时
两路都是一条，但**理由不同**——两遍是「归档卷是一条顺序扫」，幂等那一道是「`--io-mode` 点名」。
一个 `chosen_by` 说不出这个分岔，报告就会把用户自己按下的那一下说成归档卷天生如此。
`Display` 因此只在两路**不等**时印第二句（目录卷全部相等，归档卷一个也不相等）：

```
介质 无寻道惩罚（固态盘） · 读取并发 32
介质 无寻道惩罚（固态盘） · 读取串行（归档卷是一条顺序扫） · 幂等那一道并发 32
介质 无寻道惩罚（固态盘） · 读取串行（归档卷是一条顺序扫） · 幂等那一道串行（--io-mode 点名）
```

三行都是真机跑出来的原样。

### 读取层的并发那一支不再问容器：`Reader::independent`

从前 `read::reads` 按 `reader.directory_root()` 分岔，拿不到卷根（即归档卷）就兜底按回串行。
现在分岔的依据只剩「点名几条」，两种容器共用同一条并发路：

```rust
pub fn independent(&self) -> Result<Reader>  // 目录卷抄一份卷根；归档卷另开一个文件句柄
```

每条读取线程拿一份自己的读取端，`Concurrent::spawn` 收 `Vec<Reader>`。目录卷那一支因此
**也**换了写法（从前是预先算好一张 `Vec<PathBuf>`，现在走 `Reader::read`），交出的字节与
次序一格没变——`serial_and_concurrent_hand_over_the_same_bytes_in_reading_order` 两种容器
各跑一遍钉住这一条。`directory_root()` 连同它文档里那句「归档卷的成员待在一个游标背后，
因此并发读无从谈起」一起删掉了：那正是本票推翻的话。

**开不出那么多句柄就用开出来的那几条**，开出的不到两条就退回串行（一条时并发与串行本来
就是同一件事，零条时并发那一支根本走不动——没有线程去领号）。读取层的规矩是
「读不出来是一个结果，不是一个错误」，开不出句柄同理——在这里当场失败会毁掉一整卷，
而少几条读取只是慢一点。**降下来的这个条数不进报告**：报告印的是**计划**，
真派出去几条是读取层的实况，两者可以不等——记进 **Q98**，那条与 `12` 号票同一族
（有了句柄上限之后这两个数会按设计常态不等）。

`Member` 加了 `#[derive(Clone)]`：并发那一支要把成员表整个搬进线程里（线程活得比那次借用长）。
归档成员的 `entry` 是**中央目录里的下标**，另一个句柄照样指得回同一个成员——这是整条路
成立的前提，写进了那个字段的文档。**代价是一条新的竞态**：成员表出自开卷那个句柄，
字节出自重开的那个，两次之间源归档被换掉就会静默读到别的字节。本票**没有加校验**，
记进 **Q99**。

### 指纹逐字节不变靠的是哪一条

**并行的是解，不是喂。**`volume_fingerprint` 那个循环一个字没改：它按 `read.index` 的次序
逐个喂 `SourceHasher`，而读取层的交付本来就有序（`Concurrent::next` 用 `early` 那张表按序号
放行）。改的只有一处——并发度从 `io.readers.count` 换成 `io.fingerprint.count`。

seam 上量它的形式只有一个（指纹不进报告）：**换一种读法重跑，这一卷照旧被跳过**。
`tests/concurrency.rs` 的 `an_archive_is_still_skipped_when_the_fingerprint_pass_changes_how_it_reads`
两个方向各跑一趟——串行写下的并发读得回，并发写下的串行也读得回；顺带断言
`decodes == 0` 与输出逐字节没动，「跳过的依据一项不少」因此也在这条里。

真实素材上另验一遍：棋魂完全版（230 成员，609 MB）`--io-mode serial` 与
`--io-mode concurrent` 各出一份 CBZ，**成员名单相同、230 张逐张 blake2b 相同、
文件大小同为 34,529,786 字节**；两份互相当上一趟重跑，两边都报「幂等命中」。

### 中止仍停在成员边界上（Q47）

并行没有动这条性质：交付按成员序号有序，`break` 因此落在一个真正的成员边界上；走出循环
把 `Reads` 丢掉，`Drop` 关闸并 join，几条读取线程当场收摊。**新出现的只有一件**——抢跑解出来的
那几个成员的字节被丢掉，那是浪费的 I/O，不是正确性。

Q47 点名「下一张动幂等或指纹的票」判「要不要为中止另立一个两支的返回类型」。
**判定：不立。**理由与 Q47 原文一字不差（`fingerprint` 那一格本来就是 `Option`，
再套一层的两个 `None` 含义不同；另立类型是给这一段加一个只在中止时用得上的形状），
而并行**没有给这条添任何新的理由**：那份喂了一半的哈希仍然走不出这一卷。

### Q85：判过了，不改，而并行让这条理由更强

Q85 点名「下一张动读取层并发的票（`p2-loose-ends/11` 就在那一带）」。
**判定：不动**——报到时攥着在途字节额度是**对的**。提前把 `Read` 拆开、把额度交出去，
背压就从「已读未算完」松成「已读」，通道白限（`read::Read` 的 `_permit` 文档明写这一条）。
幂等那一道并行之后这条更值钱：归档卷上现在有几十条读取线程在解 deflate，若报到时不再占额度，
观察者一慢，读取层就会把整卷囤进内存。rayon 工作线程那一半同理，且它根本不在这一道上——
幂等那一道没有 `par_bridge`。

### 一卷同时开几个句柄（12 号票要的那个数）

**`1 + min(IoPlan::fingerprint.count, 这一卷的成员数)`**：卷自己那一个（`Volume::reader`，
那一道里它闲着），加上一条读取线程一个。随**点名的并发度**与**这一卷的成员数**变，
不随卷数变，且只活在幂等那一道之内——`Reads` 一析构就全收掉。本机（32 核、NVMe）上
230 成员的归档卷是 **33** 个。条数由 `src/read.rs` 的
`a_concurrent_read_holds_one_reader_per_worker` 钉着。

**本票不划那道线**（票面明禁），记进停车场 **Q96**，交给 `p2-loose-ends/12`。

### `CONTEXT.md`《I/O 与并发》改了哪一句

原文「归档卷不在这套里——一个 ZipArchive 就是一个游标，读取恒串行，点名也改不了」
拆成两条，并写明松口为什么只对幂等那一道：**那一道没有可与之重叠的计算**（只解压、喂哈希，

词汇表加了一个新词**一路读取 (Readers)**，`读取计划 (IoPlan)` 那一条跟着改成「两路」。

**ADR 0009 一个字没动**：Q78 当初写「也要改 ADR 0009 的口径」——查过了，那份 ADR 里
没有「归档卷恒串行」这句话，这条决定从头到尾只住在 `CONTEXT.md` 与 `IoPlan::decide` 的注释里。

### 实测

`--io-mode serial` 与默认在**归档卷**上唯一的差别就是幂等那一道派几条（两遍本来就串行），
两档因此是同一批里的一次 A/B，不是两次独立测量。数进 `docs/measurements.md`
《三段各占多少》与《端到端吞吐》。

| 卷 | 入 MB | 幂等那一段（串行→并发） | 整卷墙钟（串行→并发） |
|---|---|---|---|
| 棋魂完全版 | 609 | **1758 → 288 毫秒（6.1 倍）** | 5990 → 4520（快 24.5%） |
| 哆啦A梦 8K | 1371 | — | 33734 → 29632（快 12.2%） |
| N和S 56 卷 | 423 | — | 26859 → 25892（快 3.6%） |

而那一道正是本票动的那一道。

**收益随源字节走，不随页数走**：N和S 页最多（1414）而省得最少——56 个卷摊掉 423 MB，
一卷只有 7.5 MB，那一段本来就短。

**四档目标一个字没抬**——那是拍板的事。整件记进 **Q97**。

#### Q47 — 幂等那一道被中止时，`volume_fingerprint` 回的是一份**喂了一半**的哈希

- **From:** 票 `p1-session/04`
- **Kind:** 确实拿不准的单项
- **Where:** `src/lib.rs` 的 `volume_fingerprint`（循环头上的中止检查点 `break` 掉）
  与 `process_volume`（幂等那一段的 `timed` 闭包）
- **Why it did not block:** 那个值**走不出这一卷**：`process_volume` 紧接着问一次闩，
  是中止就整卷回 `None`，而闩只升不降，两次问必得同一个答案。中间那一步也不白跑——
  `can_skip` 被一个 `if !events.aborting()` 罩着；罩它是为了**中止之后别再做 I/O**
  （问一次幂等要开上一趟的输出容器、逐页读回记录），不是怕那个答案错——
  它横竖会跟着整卷一起被丢掉。
  真要在类型上拦死，得让 `volume_fingerprint` 回 `Option<Fingerprint>`；
  可 `fingerprint` 那一格**本来就是 `Option`**（`--no-metadata` 关掉整道时是 `None`），
  再套一层就成了嵌套的 `Option`，而两层 `None` 的含义完全不同（「这一道没走」与「被中止了」）。
  要分得开就得另立一个两支的类型，那是给这一段加一个只在中止时用得上的形状。
- **What this ticket actually did:** **让它回一份用不上的哈希，靠紧接着那一句
  `return Ok(None)` 把它连同整卷丢掉**；`can_skip` 那一句另罩了一层
  `if !events.aborting()`，那一层买的是「不再做 I/O」，不是正确性。
  `process_volume` 的《中止：回 `None`》那一节写清了「各段不把『我是被中止的』
  当返回值往上传」这条通则——依据就是闩只升不降。
  用例那一侧钉的是循环头本身：`aborting_in_the_fingerprint_pass_never_lets_the_passes_after_it_start`
  比的是**这一道停在第几步**，把 `break` 删掉它当场红。
- **Whose call:** 下一张动幂等或指纹的票（要不要为中止另立一个两支的返回类型）
- **处置：** 待处理。

#### Q78 — 归档卷的幂等这一道是三段里第二大的一块，全是把源字节再串行解压一遍

- **From:** 票 `p0-hardening/13`
- **Kind:** 剖面量出来的结构性开销
- **Where:** `src/lib.rs` 的 `volume_fingerprint`；`src/read.rs` 的 `Reads::Serial`；
  `src/source.rs` 的 `Reader::Archive`；`CONTEXT.md` 的《I/O 与并发》末段
- **Why it did not block:** 棋魂（归档）上把两个开关各关一次，量到幂等那一段是三段里
  第二大的一块，仅次于第一遍——数与推法在 measurements 的《三段各占多少》。
  那一段几乎全是 deflate：成员绝大多数是 PNG，压缩比接近 1，白解一遍；
  喂哈希本身在《分阶段耗时剖面》里读作 0.0%。它没有可与之重叠的计算，整段暴露在墙钟上。
  **收它要改一条领域决定**：`CONTEXT.md` 明写「归档卷不在这套里——一个 ZipArchive
  就是一个游标，读取恒串行，点名也改不了」。技术上绕得开（同一个文件开几个独立句柄，
  各解各的成员，哈希那一端仍按成员序喂），但那要改 `IoPlan` 的取值、改报告里印出来的
  「读取串行（归档卷是一条顺序扫）」那一行，也要改 ADR 0009 的口径——
  是一张自己的票，不是一次优化。本票的红线是「不改变任何判定结果」，这条越过了它。
- **What this ticket actually did:** **量了，写进 measurements，没动。**幂等那一道
  一个字节都没改，`IoPlan` 与报告那一行照旧。本票的四处优化全在计算侧
  （判据的两处、量化的取整、转灰的一格缓存）；`src/read.rs` 只挨了两处插桩，
  读取策略与交付次序一格没动。

#### Q85 — 报到时手里仍攥着 rayon 工作线程与读取层的在途字节额度

- **From:** 票 `p2-loose-ends/02`
- **Kind:** 我确实拿不准的单项
- **Where:** `src/lib.rs` 的 `Compute::page`（`page_failed` 与 `step` 那两句）；
  `src/read.rs` 的 `Read` 与它那格 `_permit`
- **Why it did not block:** 本票要的是「持锁处调观察者当场炸掉」，而这两样**都不是锁**：
  哨兵（`progress::LockSentinel`）因此照设计不管它们，五处报到一处都不触发。
  观察者久不返回时它们也不死锁——攥着的额度只会把读取层背压闸住，
  而消费不动就别再读多半正是想要的。真要让它不闸住，得在报到之前先把 `bytes` 与额度交出去，
  那是改第一遍的形状，不是加一个检查。这一半本来就写在票面上：**本票不动这两样**。
- **What this ticket actually did:** **没有动。**把这条边界**写进了哨兵自己的文档**
  （`LockSentinel` 的《只守卷缓存那一把》），说清哨兵管到哪儿、为什么这两样不在里面——
  原先它只是 Q40 里的一段话，Q40 了结之后就没有出处了。
- **Whose call:** 下一张动读取层并发的票（`p2-loose-ends/11` 就在那一带）
- **处置：** 待处理。
