## 落地记录

### 判定：**不划那道线**

自变量不是点名的卷数，是**并发度**。一趟同时开着的句柄峰值是

```
min(并发度, 这一卷的成员数) + 3
```

三格：正在处理的那一卷（归档 1 / 目录 0）、正在读的那几个成员、写出那一侧至多两个
（缓存溢写 + 输出容器）。主项在两种容器上同形，归档卷的幂等那一段就是
`1 + min(IoPlan::fingerprint.count, 成员数)`——Q96 记的那个数。
并发度至多是核数，因此峰值封顶在**核数加个位数**：本机（32 核）上 230 成员的归档卷
在幂等那一段是 33 个。而一个进程能同时开着的句柄比它多几个数量级——Windows 上实测
十万个同时攥着还没撞上限，最紧的那一档（Linux 的默认软上限 1024）也要**上千个核**才够得着。

划一道线只能划在核数上：那等于为一个够不着的上界引一套句柄记账，
再把 `--io-mode concurrent` 按这套记账夹第二次。**买不到东西，因此不买。**

**前提是前两张票落下的那两笔，本票一笔都没动**：`volume-discovery/01` 让预扫一个句柄都不攥、
卷按路径逐个重开（那一格因此是 1，不是点名的卷数）；`p2-loose-ends/11` 让幂等那一道
同一卷开出几个句柄（那一格因此带一个乘数，而乘数是并发度，不是卷数）。

### 第 3 条为什么不适用

原文：「撞上去的错不是底层的原话，是说得出**「点名太多了」**的那一种」。

不划线之后**没有「点名太多了」这回事**：点名的卷数不是自变量，把句柄不够说成
「点名太多了」是**假话**——点一个卷与点三百个卷，峰值是同一个数。还够得着的两条路各自的形状：

- **幂等那一道开不出句柄**：不是错误。读取层用开得出来的那几条接着做，开出的不到两条
  就退回串行（`read::reads`）。这一支根本不报错，没有「底层的原话」可言。
- **卷自己那一个开不出来**：`source::open` 的「打开 X」加操作系统那一句
  （Unix 的 `Too many open files`，Windows 的「系统打开的文件过多」），走**卷级失败**——
  这一卷记一笔，其余卷照做。**它确实是底层的原话，而这一次留着原话是对的**：
  那句话说的是实话（进程的句柄额度被耗光了），而这条验收要的那个替代品是假话。
  用户手上真有的那个旋钮已经写进账里：`--io-mode serial` 把峰值按回 1。

因此这一条**没有可做的动作**：既没有一道线可撞，也没有一句该改写的原话。

### 新用例长什么样，以及它为什么不会静默失效

问的时刻是**每一卷开工那一条事件**：那一刻上一卷已经收摊、这一卷还没按路径重开，
整趟任何一处攥住某个归档不放都会在这里露馅。两个平台各答一半，照
`a_survey_keeps_no_archive_open` 的办法：Linux 数 `/proc/self/fd`，
Windows 问「装着这些归档的目录还改不改得动名」（改完当场改回来，观察者不返回、
被测那一趟就走不下去，因此两句之间没有第二个人看得见它换过名字）。

**同一对问题在「开遍」那条事件上再问一遍，那是阳性对照**：那一刻这一卷正开着，
两句都该报「还开着」。少了它，这条用例会在「开工那条事件挪到重开之后」这类改动下
**静默失去检出力**——问的时刻不对了，而两句照旧一片安静。本机（Windows）上对照那一半
跑的是重命名那一句：每一卷的每一遍都问一次，次次改不动名，因此这条用例的检出力是**验过的**，
不是推出来的。

两个问的时刻**都出自 `run` 那条线程**（开工与开遍都由 `process_volume` 自己发）。
阳性对照起初挂在「走完一步」那条事件上，**评审 Standards 轴指出它站不住**：那一条
从计算线程上报出来、同一卷内可能并发到达（`progress::Event::Stepped` 的文档明写），
两条线程同时改名会与自己撞车。改挂到「开遍」那一条上，两个时刻于是都是单线程的。

夹具取的是这批里最便宜的一张页（`TINY` 配 `--fit inside` 不放大、`full_bleed_gradient`
那圈墨边让裁边也不起作用）：本条问的是开卷、读、写出这几笔，不是像素。
32 卷整条用例量不出可辨的墙钟增量：加它之前这个二进制 11.6 秒，加完 8.4 秒——
同一台机器上的抖动比这一条本身大。

#### Q42 — 点名的每一个归档卷，整趟都占着一个打开的文件句柄

- **From:** 票 `p1-session/03`
- **Kind:** 票面没想到的第三种情形
- **Where:** `src/survey.rs` 的 `Survey::of`；`src/source.rs` 的
  `Reader::Archive(zip::ZipArchive<BufReader<File>>)`
- **Why it did not block:** 票面要「枚举结果交给管线复用，不扫两次」，而归档卷那次枚举**就是**
  `ZipArchive` 本身——中央目录读出来之后住在它里面，放掉它就等于要再读一遍。

  （目录卷不占：它的读取端只是一个 `PathBuf`）。眼下不咬人：处理范围是用户点名的子集
  （ADR 0009），一次几十个卷，而 Windows 的句柄上限是百万级、Linux 默认软上限 1024。
  真要摘掉这笔代价，只有让枚举与「取字节的那一半」分家——那要改 `source::Volume` 的形状，
  是一件独立的事。内存那一侧同量级、更小：一份中央目录约每成员几十字节。
- **What this ticket actually did:** **认下这笔代价，写进 `src/survey.rs` 的模块文档**
  （《要认的代价》那一段），并说清它是「不扫两次」的必然结果而不是疏忽。
  没有引任何句柄池或惰性打开。
- **Whose call:** 拍板的人（点名上千个归档卷要不要支持）
- **处置：** 待处理。**这笔代价本身已经由 `volume-discovery/01` 消掉**：它走的是本条挂出来的
  「分家」那条出路，但不是本条设想的形状——没有改 `source::Volume`，而是**预扫数完就把整个卷
  放掉、处理那一卷时按路径重开**（`Surveyed` 里只剩路径与两个数）。现状因此是：预扫开完一个
  归档句柄都不攥着（`src/survey.rs` 的 `a_survey_keeps_no_archive_open`，300 个卷），
  常驻中央目录同步归零，一趟同时开着的从「点名几个就是几个」变成「正在处理的那一卷一个」；
  换来的正是本条写着的那一笔——「放掉它就等于要再读一遍中央目录」，现在照付，
  而它随**一个卷**长、不随点名的卷数长。
  **本条仍留在这里**：要判的那件事（还需不需要一道句柄上限）归 `p2-loose-ends/12`，
  那张票明写着「收停车场的 Q42」，本票不替它拍板。它的票面前提（「预扫打开的归档卷全部留到
  各自被处理时」）与第 4 条验收（「中央目录不许读第二遍」）自本票起都不再成立，
  见 `volume-discovery/01` 落地记录的《票面与队列》。

#### Q96 — 一卷同时开着的归档句柄从 1 涨到 `1 + min(幂等那一道的并发度, 成员数)`

- **From:** 票 `p2-loose-ends/11`
- **Kind:** 票面点名要如实记下来的那个数
- **Where:** `src/read.rs` 的 `reads`（并发那一支给每条线程发一份读取端）与
  `Reader::independent`；`src/source.rs` 的 `Reader::Archive`；停车场 Q42
- **Why it did not block:** 本票让幂等那一道在归档卷上并行，办法是**同一个文件开几个独立句柄**。
  一卷同时开着的因此是：
  **`1 + min(IoPlan::fingerprint.count, 这一卷的成员数)`**——卷自己那一个
  （`Volume::reader`，那一道里它闲着），加上一条读取线程一个。
  它随两样变：**点名的并发度**（`--io-mode concurrent` 或 auto 探到固态盘时等于核数，
  机械盘与未知、以及 `--io-mode serial` 时是 1）与**这一卷的成员数**（比成员还多的线程不开）。
  它**不随点名的卷数变**——`volume-discovery/01` 之后一趟只有正在处理的那一卷开着句柄。
  也**只活在那一道之内**：`Reads` 一析构，几条读取线程连同它们的句柄一起收掉，
  两遍那一路照旧一个句柄。本机（32 核、NVMe）上 230 成员的归档卷因此是 **33** 个。
  条数由 `src/read.rs` 的 `a_concurrent_read_holds_one_reader_per_worker` 钉着。
- **What this ticket actually did:** **把这个数记下来并用一条用例钉住，没有划任何上界。**
  票面明写「那道线不由你划」——要不要一道句柄上限归 `p2-loose-ends/12`，它收的 Q42
  正是这一族。本票没有引句柄池，也没有把并发度按句柄数再夹一次。
- **Whose call:** 票 `p2-loose-ends/12`（句柄上限那一张）
- **处置：** 待处理。

#### Q98 — 句柄开不出来时并发度悄悄降下来，而报告照旧印计划里那个数

- **From:** 票 `p2-loose-ends/11`
- **Kind:** 路过发现（评审 Standards 轴指出）
- **Where:** `src/read.rs` 的 `reads`（`Err(_) => break` 那一支）；
  `src/medium.rs` 的 `IoPlan`/`Readers` 的 `Display`
- **Why it did not block:** 归档卷上每条读取线程要一个自己的文件句柄。开不出那么多时
  这一层**用开出来的那几条**接着做，而报告印的仍是计划里那个数（「幂等那一道并发 32」）。
  本票自己把「点名串行而实际派满核数，报告说的就不是实话了」当成设计理由，这里出现了
  同形状的一个分岔。**没让它停下来**的理由有三条：一，那是异常路径——句柄开不出来时
  多半连字节也读不出来，那一卷横竖会全员 `unreadable`；二，另一条路（开不出就整卷失败）
  更糟，读取层的规矩明写「读不出来是一个结果，不是一个错误」；三，`IoPlan` 是**计划**，
  不是实况——`ChosenBy` 答的是「这个数是谁定的」，不是「最后真派了几条」，
  要报实况得让读取层把结果回报给报告那一层，那是一条新的通路。
  **它与 `p2-loose-ends/12` 同一族**：一旦有了句柄上限，计划的数与实际的数就会**按设计**
  常态不等，那时这条才真正咬人。
- **What this ticket actually did:** **把这条分岔写进 `reads` 的文档**（「降下来的这个条数
  不进报告」，并指着本条），代码没动，也没有为它加通路。降级那一支**没有用例**——
  要造它得逼操作系统拒发句柄，portable 的做法本票没找到。
- **Whose call:** 票 `p2-loose-ends/12`（划了上限之后要不要让报告说实况）
- **处置：** 待处理。

**本票的处置（三条）**

- **Q42 —— 了结。** 它挂出来要拍板的是「点名上千个归档卷要不要支持」。
  **答案是：已经支持了，而且不是本票支持的**——`volume-discovery/01` 把「点名 N 个就占 N 个」
  消成「正在处理的那一卷一个」之后，点名的卷数就不再进这笔账。本票只做了两件事：
  把这个结论钉成一条用例（32 卷、每卷开工时零句柄），把这笔账收进一处。
  Q42 原文写的那条出路（「让枚举与取字节的那一半分家，那要改 `source::Volume` 的形状」）
  **走成了另一个形状**：没有改 `source::Volume`，改的是预扫留下什么。
- **Q96 —— 了结。** 它记的那个数一格没变，`1 + min(IoPlan::fingerprint.count, 成员数)`
  现在住在 `source::Reader` 的《一趟同时开着几个句柄》里，本机 33 个那句连同
  平台上限一起进了 `docs/measurements.md`。它点名要本票拍的板：**不划上界**，理由见上。
- **Q98 —— 了结，判定不改。** 它自己写着「一旦有了句柄上限，计划的数与实际的数就会
  **按设计**常态不等，那时这条才真正咬人」——**那个前提本票判定不会出现**，因此这条
  永远停在异常路径上，而它当初没让队列停下来的三条理由（异常路径、另一条路更糟、
  `IoPlan` 是计划不是实况）本票一条都不推翻。`reads` 的文档里那句「见停车场 Q98」
  改成就地写清这条判定，条目了结之后不留悬空引用。
  **留下一笔如实说**：降级那一支仍然**没有用例**（要逼操作系统拒发句柄，portable 的做法
  仍然没有）。不为它另开条目，是因为它守的那条路已经判成异常路径且不改；
  哪天真划了线，重开的是 Q98 这条本身。
