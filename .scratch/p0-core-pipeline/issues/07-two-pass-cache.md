# 07 — 两遍管线与缓存

**What to build:** 把管线改成解码一次：第一遍完成解码、几何与缩放并算出判据曲线，同时把缩放后的 8 位灰度图缓存起来；第二遍只做量化与编码，不再碰源页。

这张票不改变任何逐页判定结果，改变的是解码次数与内存行为——它为下一张票的卷级决策铺路。依据见 ADR 0005：解码一次，缓存缩放后的图。

缓存内存优先，超出 `--cache-budget` 溢写临时文件，只活在一次运行之内。

**Blocked by:** 06 — 位深决策：逐页判定与灰阶上界

**Status:** resolved

- [x] 每页只解码一次，可用计数验证
- [x] 缩放后的图经 LZ4 缓存，第二遍从缓存读
- [x] 超出 `--cache-budget` 时溢写临时文件，运行结束后清理
- [x] 中断后不留下孤儿临时文件，或再次运行时能自行清理

## Comments

两遍落在 `lib.rs` 的 `first_pass` / `second_pass` 两个函数上，中间空出汇总那一段并标了注：
卷级上包络、迟滞与离群页识别（08 号票）要接的就是那里，接上去时第二遍已经不必回头碰源页——
这正是本票替那一张铺的路。缓存这一层的词汇（第一遍/第二遍、汇总、缓存、缓存预算、溢写）
进了 `CONTEXT.md` 的《管线》，含义在那里，理由仍只在 ADR 0005。

**解码计数记在解码这个动作上，不记在调用方的循环里。** `decode::decode` 收进 `Decoder`，
解一页记一次，`VolumeReport::decodes` 取它的读数。记在 `first_pass` 的循环里也能让
`decodes == pages.len()` 成立，但那是**构造出来的**相等——它与 `pages.len()` 由同一次迭代
一起长出来，永远不会不等，守卫也就守不住任何东西。记在解码器上之后，解码只此一条路，
第二遍回头解一页立刻被这个数抓住（用突变验过：多解一遍，计数从 3 跳到 6，用例失败）。

`decodes` 越出了 spec 给 `Report` 固定的字段表，这是有意的：票面要的「可用计数验证」，
在 `run` 这个 seam 上只有报告这一个可观测面。`PageReport` 的 `size`/`scaling`/`scores`
同样不在那张表上、由 04 与 05 号票加进来——那张表是下限不是上限。

**缓存里每页的序号跟着页走**（`CachedPage { report, slot }`），不由第二遍 `enumerate()`
数出来。眼下页序与缓存序恰好重合，但 ADR 0005 决定第 4 条说彩页在彩色 profile 下第一遍
即写出、不进灰度缓存——10 号票落地当天两者分家，而数出来的序号会**静默**把另一页的像素
写到这一页的位置上，没有任何断言拦得住。

缓存（`src/cache.rs`）存的是**参照本身**——判据算过的那张缩放后 8 位灰度图，LZ4 压过。
预算按压缩之后的常驻字节算，那才是真正占着内存的量；判的是「这一页放进去会不会越过预算」，
因此单页大过整个预算时它自己溢写，已经在内存里的页不受牵连。记账排在落定之后：
溢写写盘失败时，用量不该记下一页其实并不存在的缓存。

**解出来的长度必须对得上。** `lz4_flex::decompress` 收的是「至多这么大」——块坏掉时它给回
短一截的缓冲而不是报错，而 `GrayImage::new` 只有 `debug_assert` 拦着，release 下那截短缓冲
会一路流进量化与编码。`unpack` 里的那句 `ensure!` 是这条路唯一的守卫。

**溢写文件是匿名临时文件**（`tempfile::tempfile_in`）：Unix 上建出来立刻 unlink，
Windows 上带 delete-on-close 标志，两边都由操作系统在最后一个句柄关闭时收走。中断时句柄由
内核关，所以票面那条「或再次运行时能自行清理」的退路用不上。**这一条在 CI 上是空的**：
自动用例只验到「缓存一放手，溢写目录就是空的」，真强杀那一半是手工验的——Windows 上
运行中临时目录多出一个文件，`Stop-Process -Force` 之后回到零。要补自动化，得让溢写目录可点名，
那是一个眼下没人要的开关。

**dry-run 只记账，不留页**（`Retention::Account`）。它没有第二遍，留下的字节没人取，
但 `--cache-budget` 撑不撑得住仍要预告得出来（spec 的 story 6）——所以照压、照按预算算账，
只是不留块，也就不建临时文件。`--dry-run --cache-budget 0` 于是会说「临时文件 338.3 KiB」
而一个文件都不建：dry-run 那句「不写输出」在命令行这一路是连临时文件都不建，
峰值内存也不为一次预演白占。
用例守住两头：只记账那一遍不建文件、取页即报错；两种 retention 给出同一份用量。

`--cache-budget` 收纯字节数或带 K/M/G 后缀（按 1024 进位，`B`/`iB` 两种尾巴都收），
解析在库里（`CacheBudget::parse`），CLI 只递字符串——与 `--filter`、`--bit-depth` 同一套分工。
报告里的单位跟着标 **KiB/MiB/GiB**：进位按 1024 却标 KB/MB/GB，报告里的数就与用户敲进去的
那个数不是同一个量。

**回归这一条靠既有用例守住，不是黄金快照。** 判定、写出的字节、各页的判据值全部未变，
34 条既有用例一条没改地通过——它们本就逐条断言了写出的像素、位深、颜色类型与判定。
真正的快照回归（spec 的《黄金回归》）是 15 号票，本票没有做新旧两份构建的对照。
溢写路径另外单验一遍：同一卷在默认预算与 `--cache-budget 0` 下写出的字节相同，判定也相同。
