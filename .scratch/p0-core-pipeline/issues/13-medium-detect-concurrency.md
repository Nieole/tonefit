# 13 — 介质探测与并发

**What to build:** 读取层与计算层分离。介质按路径映射到所在卷再探测寻道惩罚：有惩罚时读取串行，无惩罚时并发。计算层用 rayon 满核，有界通道按字节预算背压。长任务显示进度。

依据见 ADR 0009：处理点名的子集，介质按路径探测。同一次运行里不同路径可能落在不同介质上，判定不能一次性做。

**Blocked by:** 08 — 卷级上包络与迟滞

**Status:** resolved

- [x] 介质探测按路径进行，同一次运行中不同路径可得到不同结论
- [x] 有寻道惩罚的路径上读取串行
- [x] 无寻道惩罚的路径上读取并发
- [x] `--io-mode` 可覆盖自动探测
- [x] 有界通道按字节预算背压，峰值内存不随并发度线性增长
- [x] 探测失败时退到保守策略并在 `Report` 里说明
- [x] 长任务显示进度

## Comments

**探测分成两步，缓存挂在中间那一步上。**路径 → 读取通道（便宜，每卷一次），读取通道 → 寻道惩罚
（贵，按通道缓存）。合成一步的话缓存就无处可放——探测本身已经把贵的那一半做完了。
ADR 0009 的《后果》点名要缓存（「每页查一次挂载表不可接受」），`medium::Probes` 的形状就是那一句。
中间那个东西在 `CONTEXT.md` 里叫**读取通道**：Windows 上是挂载点，Linux 上是块设备号。

**平台那一对做成了可换的函数指针**（`medium::Probes::with`）。探测要碰真实存储栈，而票面头一条、
缓存那一条、退到保守那一条与碰的是哪块盘无关——真机上只有一块盘可探，那三条在 `run` 这个 seam 上
根本量不出来。另有一条用例拿本仓库自己的路径跑一遍**真的**探测：不断言答案，只钉住那条 FFI 不崩。

**`--io-mode` 的取值是 `auto | serial | concurrent`，不是 `hdd | ssd`。**ADR 0009 的备选方案里
否掉的那一条是「让用户用命令行开关声明介质类型」——它否的是拿声明**代替**探测。这里是探测之上的
一道覆盖：用户改不了盘的物理事实，改得了的是这一趟怎么读。覆盖之后探到的介质仍照实进报告。

**归档卷恒串行，而且这一条排在覆盖项前面**（`IoPlan::decide`）。它不是性能上的让步，
理由与代价见那个函数的注释。报告里写着「读取串行（归档卷是一条顺序扫）」——
`--io-mode concurrent` 在归档卷上不生效这件事不能只表现为「点了没反应」。

**闸开在读之前，且领序号与占字节在同一把锁里**（`read::Throttle`）。后半句是这道闸不死锁的全部
理由，写在那个类型的文档上。另一半理由在调用方那侧：**同时攥在手里的不能超过预算**，
写在 `read::Reads` 上。正常用法撞不上它，撞上它的是「先 `collect` 成一个 `Vec` 再算」——
而那正是有界通道要拦掉的东西。写用例时先撞上过一次，是活的。

**在途字节的预算不与 `--cache-budget` 共用一个数。**那个限的是两遍之间存下的**参照**（ADR 0005），
这个限的是还没解码的**源字节**，两者在管线上前后不相接；绑在一起会让「限制内存占用」这一个旋钮
同时动两个不相干的量。64 MiB 的来路见 `read::BUDGET`。

**「峰值内存不随并发度线性增长」说的是通道那一摊。**计算层每条线程手里一张解好的图，那一摊随核数走，
且无从避免——「计算层用 rayon 满核」要的就是它。有界通道拦掉的是另一件事：没有它，
固态盘上的读取层会把整卷读进内存。两者分得清才说得清，因此这一条在 `read.rs` 的单元用例里量
（那里量得到在途字节），不在 `run` 那个 seam 上。

**并发之下要指名道姓的地方，一律取序号最小的那一个，不取最先撞上的那一个。**三处：
几何门是哪一页关的（`fetch_min`）、`--dither fs` 撞上门时报的是哪一页、第一遍出错时报的是哪一页
（页序归位**之后**才短路取错）。换一次调度就换一个答案的报告等于没有答案，而后两支上
连报告都没有，那句话是唯一的线索。

**候选集的裁剪挪到了第一遍收尾。**顺着做时是「一页关上门，回头把前面几页的抖动候选裁掉」；
并发下改成「各线程尽力用当下那一套，收尾按**最终**的门统一裁一遍」。结果因此与线程先后无关，
而「候选集全卷同一套」到汇总看见它的时候仍然成立——上包络与迟滞靠的正是这一条。

**第二遍也满核，但分批**（见 `second_pass`）。它原先是纯串行的一条尾巴，卷长了之后占的比重不小。
写出仍按阅读顺序，彩页那一支借第一遍编好的字节而不复制（`Cow`）——那一摊本来就不受
`--cache-budget` 约束（ADR 0010），再翻一倍不合适。

**幂等那一道也走同一个读取层。**它把整卷的源字节读一遍（`CONTEXT.md` 说了它「不是免费的」），
在固态盘上没道理还串行读。读取层因此**按序号有序交付**：计算层其实不在乎顺序，
有序是为了这个调用方——源哈希是有序的，乱一位整卷的指纹就变了。

**认下的一处不确定：缓存的常驻/溢写分法不再可复现。**第一遍乱序满核跑，谁先进缓存就随调度而变，
`CacheUsage` 的 `resident` 与 `spilled` 因此两趟可能不同。总量（`pages`、`raw`、`stored`）
与写出的字节一个不差。要让分法确定，存入就得按页序串起来——那正是满核要拆掉的东西。
`cache::PageCache::insert` 的文档写着这一条，用例的断言也照它收窄。

**对 spec 那个「故在此固定」的 `Request` 形状的一处偏离**（与 12 号票同一类）：
`Request` 多了一个 `progress`，而 spec 的覆盖项里没有它。story 30 要的是「看得到进度」，
而 `run` 是唯一的入口——观察者不进 `Request` 就没有第二条路进得去。它不是覆盖项：
它一个像素都不改，也因此不进参数哈希（`metadata` 那一侧有用例钉住）。
做成 trait 而不是直接放一个进度条，是因为往库里塞 indicatif 就等于让它替 CLI 决定输出的样子，
而用例也没法在不开终端的情况下问「它到底报到了吗」。

**Windows 那一侧走 `DeviceIoControl` 问存储栈本身**，不认型号名、不看转速表；查询句柄按
**0 访问权限**打开，因此不要管理员权限。网络盘先被 `GetDriveTypeW` 挡下。Linux 走 sysfs 的
`queue/rotational`。别的平台一律未知。细节在 `medium::platform`。

**这一票最要紧的一条用例是「读法不改变结果」。**串行读一趟、并发读一趟，写出的每一个字节、
逐页的判定、几何门、解码次数全都一样。第一遍从一页一页顺着做改成了乱序满核跑，
而这些改动对外应当完全不可见——这一条不过，上面所有的话都不算数。

**没做的一件事：输出侧的介质没有探测。**写出是顺序的、一个卷一个容器，没有并发可言，
探了也无处可用。ADR 0009 举「源卷在仓库盘、输出在系统盘」是为了说明**按机器判定**行不通，
不是说输出侧也要各判各的。
